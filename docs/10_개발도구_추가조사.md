# Claude Code 개발 도구 추가 조사

조사 기준일: 2026-11-01. 제작자 저장소와 공식 문서를 확인한 조사이며, 설치·실행·사용자 설정 변경은 하지 않았다.
기존 `01_개발용_추천.md`의 LSP, Serena, Playwright MCP, Superpowers 등과 중복을 비교했다.
아래 우선순위는 문서에 근거한 선택 판단이다. 도구 간 성능이나 비용 절감을 직접 측정한 결과가 아니다.
`우선 검토`도 해당 작업이 있을 때의 추천이며, 모두 설치하는 구성이 아니다.

## 먼저 고르는 기준

| 필요한 일 | 추가 후보 | 판단 |
|---|---|---|
| 문법 구조가 같은 코드를 찾거나 바꾸기 | ast-grep CLI + 공식 skill/plugin | 기존 LSP를 보완하는 우선 후보 |
| 코드 일부를 묶어 구조 검토·인수인계하기 | Repomix CLI/Explorer | 필요한 순간 사용하기 좋은 후보 |
| 웹 브라우저를 CLI로 반복 제어하기 | Playwright CLI + skills | 기존 Playwright MCP의 대안 |
| 테스트·빌드 출력이 지나치게 길기 | RTK | 실제 출력 문제를 확인한 뒤 조건부 |
| 프로젝트 특화 정적 보안 검사 | Semgrep/Guardian | 기존 보안 체계와 연결할 때 조건부 |
| 조직의 여러 저장소를 함께 검색하기 | Sourcegraph MCP | Sourcegraph 사용 조직에 조건부 |
| 별도 브라우저 에이전트 CLI가 필요하기 | agent-browser | Playwright 계열과 비교 후 하나 선택 |
| 실행 중인 Flutter 앱을 진단하기 | Dart and Flutter MCP server | 해당 SDK 사용자에게 우선 |
| 로컬 MCP 서버 여러 개의 실행 환경 관리 | Docker MCP Toolkit/Gateway | 운영 복잡성이 생겼을 때 조건부 |
| 로컬 심볼 색인·선택적 코드 추출 | jCodeMunch | Serena와 겹쳐 기본 구성에서는 후순위 |

도구 수보다 해결할 문제를 먼저 정한다.
현재 Claude Code는 MCP 도구 정의를 검색해서 불러올 수 있으므로, MCP가 있다는 이유만으로 정의 전체가 항상 문맥에 들어간다고 가정하지 않는다.
출력 크기, 실제 호출 횟수, 저장소 색인, 외부 서비스 사용료를 따로 비교한다. [Claude Code MCP Tool Search](https://code.claude.com/docs/en/mcp#configure-tool-search)

## 1. ast-grep — 구조 검색·대량 수정에 우선 검토

**유형:** 로컬 CLI + 제작자 제공 Claude Code plugin/Agent Skill. MCP는 별도 선택지다.

일반 텍스트 검색으로 찾기 어려운 문법 패턴을 AST로 찾는다.
예를 들면 특정 React 훅 안의 호출, 특정 인자 형태의 API 사용, 여러 파일의 오래된 문법을 추리는 작업이다.
검색 규칙을 lint 규칙이나 코드 치환으로 발전시킬 수 있다. [공식 소개](https://ast-grep.github.io/guide/introduction.html)

**기존 도구와 관계:** LSP/Serena의 정의·참조·심볼 편집과 달리, 여러 파일의 문법 모양을 비교하는 데 초점이 있다.
단순 이름·문자열은 `rg`, 정의·타입 관계는 LSP, 구조 패턴은 ast-grep으로 나누면 역할이 분명하다.
AST 패턴이 맞았다는 사실이 런타임 안전성이나 취약점 존재를 증명하지는 않는다.

**실행 방식:** 명시적 CLI 호출 또는 관련 skill을 선택한 Claude의 호출이다.
설치만으로 모든 검색이 ast-grep으로 바뀌지 않는다고 제작자 문서가 설명한다.
필요한 요청에서 “ast-grep으로 이 구조를 찾아줘”라고 지정하는 방식이 적합하다.

**전제·비용·데이터:** ast-grep 실행 파일을 별도로 설치해야 한다.
일반 CLI는 로컬 소스를 파싱하며, 자체 검색에 외부 LLM API가 필요하지 않다.
Claude가 규칙을 만들고 결과를 해석하는 사용량은 별도다.
온라인 Playground와 로컬 CLI는 데이터 경로가 다르므로 구별한다.

**선택 판단:** API 마이그레이션·코딩 규칙 점검을 반복하면 추천한다.
작은 저장소에서 문자열 검색만 하는 경우에는 추가 이득이 작다.
치환 전에 맞아야 하는 예와 맞으면 안 되는 예로 규칙을 확인하는 편이 좋다.
출처: [제작자 agent-skill 저장소](https://github.com/ast-grep/agent-skill), [공식 소개](https://ast-grep.github.io/guide/introduction.html).

## 2. Repomix — 필요한 코드만 묶어 전달할 때 우선 검토

**유형:** CLI, MCP 서버, Claude Code Explorer plugin/skill을 제공하는 코드 패키징 도구.

선택한 저장소의 파일을 XML·Markdown·일반 텍스트 등으로 묶어 모델이 읽을 자료를 만든다.
낯선 라이브러리 구조 파악, 제한된 디렉터리의 설계 검토, 다른 세션에 코드 자료 전달에 적합하다.
일상적으로 전체 저장소를 다시 읽는 도구로 사용하면 오히려 입력량이 커질 수 있다. [공식 안내](https://repomix.com/guide/)

**기존 도구와 관계:** Serena/LSP는 필요한 심볼을 찾고, Repomix는 고른 범위의 스냅샷을 묶는다.
지속 기억 DB가 아니며, 생성된 묶음이 원본 변경을 자동으로 따라간다고 가정하면 안 된다.
명시적으로 watch 모드를 쓰는 경우와 일회성 생성은 구별한다.

**실행 방식:** CLI는 요청할 때 실행하고, MCP는 Claude가 도구를 호출한다.
Explorer plugin은 반복 가능한 탐색 절차를 제공한다.
공식 문서상 MCP 기능은 experimental이며, CLI·skill과 MCP를 모두 설치할 필요는 없다. [MCP 문서](https://repomix.com/guide/mcp-server)

**전제·비용·데이터:** 현재 공식 FAQ는 Node.js 22 이상을 요구하며 Docker 경로도 있다.
로컬 CLI는 로컬 파일을 묶는다. 결과를 외부 모델에 전달하는 단계에서 해당 모델의 데이터 처리와 사용량이 적용된다.
공개 저장소를 가져오는 원격 모드와 웹 서비스를 로컬 사용과 혼동하지 않는다. [FAQ](https://repomix.com/guide/faq)

**범위 설정:** 기본 MCP는 호스트가 읽을 수 있는 경로를 읽을 수 있다.
공식 `--sandbox` 모드는 지정 루트 안의 읽기 기능으로 제한하지만 OS 수준 격리는 아니다.
Secretlint 검사가 있어도 결과에 민감정보가 전혀 없음을 보장하지는 않는다.
원격 저장소 설정은 기본적으로 무시되며, 이를 신뢰하도록 켜면 실행형 설정의 동작도 포함된다. [보안 문서](https://repomix.com/guide/security)

**선택 판단:** 우선 CLI 또는 Explorer 하나로, 필요한 하위 폴더만 묶는 용도가 좋다.
전체 저장소를 매번 문맥에 넣기 위한 필수 MCP로는 추천하지 않는다.

## 3. RTK — 긴 명령 출력을 줄일 필요가 있을 때 조건부

**유형:** CLI + Claude Code hook. 현재는 선택형 압축 엔진·별도 API proxy도 제공한다.

테스트 통과 목록, 반복 로그, Git 출력 등을 필터링·그룹화해서 Claude에 반환한다.
예를 들면 수백 줄의 성공 로그에서 실패와 요약을 먼저 보게 하는 목적이다.
코드를 색인하거나 프로젝트 지식을 저장하는 도구는 아니다. [제작자 README](https://github.com/rtk-ai/rtk)

**실행 방식:** CLI를 직접 호출할 수 있고, 설정한 PreToolUse hook은 Bash 명령을 RTK 명령으로 바꾼다.
이 기본 hook은 Claude의 내장 Read/Grep/Glob에 그대로 적용되지 않는다.
엔진의 추가 처리와 API proxy는 별도의 기능이므로, 기본 명령 필터와 나누어 판단한다.

**기존 도구와 관계:** LSP·Serena가 무엇을 읽을지 고른다면 RTK는 명령 결과를 얼마나 돌려줄지 조정한다.
실패 원인 조사에서 필터가 필요한 세부사항을 숨길 수 있으므로 원본 출력과 비교할 수 있어야 한다.
제작자는 원본 명령을 우회 실행하는 `rtk bypass`를 제공한다.

**비용 판단:** 출력 바이트 감소와 세션 요금 감소는 같은 수치가 아니다.
기본 필터는 프롬프트 전체나 모델의 답변 토큰을 줄이는 기능이 아니다.
`rtk gain`의 토큰 수는 추정치이므로 실제 청구액·구독 사용량 절감률로 옮겨 적지 않는다. [절감량 설명](https://github.com/rtk-ai/rtk/blob/develop/docs/guide/resources/savings-explained.md)

**배포·데이터:** Apache-2.0 전용 OSS판과 BUSL 엔진 포함판이 있으며, 둘은 같은 `rtk` 실행 파일을 사용한다.
API proxy는 별도 데몬이다. 프록시·모델 라우팅까지 켜면 단순 로컬 출력 필터와 데이터 경로가 달라진다.
제작자 문서상 일반 실행은 무료 사용을 허용하지만, 구성요소별 라이선스와 재배포 조건은 다르다.
README의 익명 telemetry는 기본 꺼짐으로 설명되어 있다. [배포판 설명](https://github.com/rtk-ai/rtk/blob/develop/docs/guide/resources/editions.md)

**선택 판단:** 출력이 실제 병목일 때 작은 범위에서 검토한다.
처음부터 proxy·자동 라우팅·외부 pipeline을 모두 켜는 기본 조합으로 추천하지 않는다.

## 4. jCodeMunch — 기존 심볼 도구가 부족할 때 후순위

**유형:** Tree-sitter 기반 로컬 코드 색인·검색 MCP. 공개 저장소가 있지만 라이선스는 별도 확인이 필요하다.

코드 구조와 심볼 메타데이터를 색인하고, 필요한 함수·클래스 구현만 반환하는 방식을 제공한다.
큰 코드베이스에서 전체 파일 읽기를 반복하는 경우에 비교 평가할 수 있다.
관계 탐색 기능이 있어도 모든 언어의 실제 실행 관계를 완전하게 분석한다고 보지는 않는다. [제작자 README](https://github.com/jgravelle/jcodemunch-mcp)

**기존 도구와 관계:** Serena/LSP와 코드 탐색 역할이 크게 겹친다.
이미 정의·참조·필요한 심볼 읽기가 잘 되면 새 MCP·색인·설정을 추가할 이유가 약하다.
Repomix와는 대량 자료 묶음 대 선택적 검색이라는 차이가 있다.

**실행 방식:** MCP를 연결한 뒤 대상 저장소를 색인하고 검색한다.
설치만으로 Claude가 모든 파일 읽기를 이 도구로 바꾼다고 가정하지 않는다.
watch·hook·추가 요약 기능도 기본 검색 기능과 별도로 구분해서 구성한다.

**전제:** 현재 패키지 메타데이터는 Python 3.10 이상을 명시한다.
색인과 원문 캐시를 위한 로컬 디스크가 필요하며, 결과가 작업 트리의 최신 상태인지 확인해야 한다.
출처: [패키지 메타데이터](https://github.com/jgravelle/jcodemunch-mcp/blob/main/pyproject.toml).

**비용·데이터:** 현재 jCodeMunch Dual-Use License는 비상업 사용과 상업 사용 조건을 나눈다.
상업 사용은 유료 라이선스 대상이므로 무조건 무료 오픈소스로 분류하지 않는다.
기본 색인은 로컬이지만 익명 집계 전송 기능과 선택형 외부 AI 요약 기능이 별도로 있다.
외부 요약을 켜면 지정한 제공자 API로 요청하며, 로컬 임베딩도 최초 모델 다운로드가 있을 수 있다. [보안·데이터 설명](https://github.com/jgravelle/jcodemunch-mcp/blob/main/SECURITY.md)

**선택 판단:** 제작자 벤치마크의 절감률을 개인 세션 비용 절감으로 받아들이지 않는다.
같은 저장소·같은 탐색 작업에서 기존 Serena/LSP 대비 실제 읽기량과 누락을 확인한 뒤 교체 후보로 평가한다.

## 5. Semgrep Guardian — 규칙 기반 보안 검사가 필요하면 조건부

**유형:** 공식 plugin에 MCP·hooks·skills를 묶은 작성 시점 보안 검사.

Claude가 작성·편집한 파일에서 취약 코드 패턴, 의존성 문제, 하드코딩된 비밀정보 등을 검사한다.
모델의 일반 코드 리뷰와 별도로 조직의 보안 규칙을 적용하고 싶을 때 적합하다.
기존 security-guidance와 자동 검사 시점이 겹칠 수 있으므로 둘을 무조건 함께 켜지는 않는다.

**현재 권장 경로:** Claude Code에서는 원격 Guardian plugin과 브라우저 OAuth 로그인을 공식 문서가 권장한다.
이 경로는 Semgrep 계정이 필요하며, 로컬 Semgrep CLI는 필수가 아니다.
로컬 plugin이나 다른 에이전트의 CLI 방식은 별도 구성이다. [설정 방식 비교](https://docs.semgrep.dev/semgrep-guardian/choose-your-setup)

**실행 방식:** 설정한 hook 또는 MCP 호출이 작성·수정된 코드를 검사한다.
Guardian은 발견 사항을 에이전트에 반환하고, 실제 코드 수정은 에이전트가 결정한다.
작성 시점 검사가 CI·PR 검사를 대체하는 것은 아니다.

**비용·데이터:** 공식 FAQ는 30일 평가판 이후 라이선스가 없으면 검사가 중지된다고 설명한다.
권장 원격 경로는 hosted scanner이므로 무료·로컬 전용 MCP로 분류하면 안 된다.
코드 처리의 구체적 보존 조건은 이번 조사에서 확정하지 않았다. [Guardian FAQ](https://docs.semgrep.dev/semgrep-guardian/faq)

**규칙:** 현재 상세 문서는 Guardian Policies와 사용자 규칙 설정을 설명한다.
개요의 일부 오래된 고정 규칙 설명보다 상세 설정 문서를 기준으로 확인한다. [규칙과 구성](https://docs.semgrep.dev/semgrep-guardian/rules-and-configuration)

**오래된 안내 주의:** 독립 `semgrep/mcp` 저장소는 2025-10-28 보관 처리되었다.
기능 자체가 사라진 것이 아니라 메인 Semgrep의 MCP 코드로 이동했으며, 현재 사용자 안내는 Guardian을 중심으로 한다.
옛 `semgrep-mcp` 패키지 설치 예시를 신규 기본 안내로 재사용하지 않는다. [보관 저장소](https://github.com/semgrep/mcp), [현재 MCP 구현](https://github.com/semgrep/semgrep/tree/develop/cli/src/semgrep/mcp)

## 6. Sourcegraph MCP — 조직의 여러 저장소 검색에 조건부

**유형:** 조직 Sourcegraph 인스턴스에 연결하는 원격 MCP.

여러 서비스에 흩어진 API 사용처, 저장소 간 변경 영향, 과거 커밋과 diff를 찾는 데 적합하다.
로컬 체크아웃 밖의 코드와 이력을 Claude가 조사해야 할 때 추가 가치가 크다.
개인 저장소 하나를 작업하는 경우에는 기본 도구로 추가할 필요가 작다.

**기존 도구와 관계:** LSP/Serena의 강점은 현재 작업 트리의 탐색이다.
Sourcegraph의 추천 이유는 단순히 심볼 검색 도구가 하나 더 있다는 것이 아니라 조직 전체 검색 범위다.
GitHub MCP로 저장소 이슈·PR을 처리하는 업무와도 목적이 다르다.

**전제:** 공식 문서는 Enterprise 요금제, 관리자 설정, `MCP#ACCESS` 권한을 명시한다.
OAuth 또는 액세스 토큰으로 인증하며 기존 저장소 접근 권한을 따른다.
사용 중인 Sourcegraph 인스턴스의 준비 상태를 먼저 확인한다. [MCP 문서](https://sourcegraph.com/docs/api/mcp)

**실행 방식:** Claude가 MCP를 호출할 때 검색한다. 파일 수정마다 자동 검사하는 hook은 아니다.
기본 endpoint와 `/all` endpoint는 도구 범위가 다르다.
추가 범위에는 정의·참조와 Deep Search 생성 등이 있어 필요한 범위를 선택한다.
출처: [Claude Code 연결 안내](https://sourcegraph.com/docs/api/mcp/client-integrations).

**비용·데이터:** Enterprise 구독과 인스턴스의 사용 권한이 전제다.
Code Finder는 인스턴스의 할당·계량 조건을 확인해야 한다.
조직 서버의 코드·검색 결과가 Claude에 전달되므로 로컬 전용 검색으로 설명하지 않는다.
판단: Sourcegraph 사용 조직이면 검토하고, 이를 위해 새 Enterprise 서비스를 도입하는 기본 조합은 추천하지 않는다.

## 7. Playwright CLI + Skills — 웹 작업에 우선 검토할 MCP 대안

**유형:** Microsoft의 브라우저 자동화 CLI + 선택적 Agent Skills. MCP 서버와 별도다.

브라우저를 열고 화면 요소를 선택하며, 로그인 흐름·스크린샷·콘솔·네트워크를 확인한다.
쉘 명령으로 브라우저를 제어하는 개발 흐름을 원할 때 적합하다.
여러 브라우저 세션도 지원한다. [공식 저장소](https://github.com/microsoft/playwright-cli)

**기존 도구와 관계:** 기존 Playwright MCP와 역할이 크게 겹친다.
CLI는 명령 중심으로 호출하고, MCP는 풍부한 페이지 상태를 도구 인터페이스로 다루는 방식이다.
이미 MCP가 잘 작동하면 CLI를 추가하는 이유를 먼저 정한다.
영구 회귀 테스트는 별도의 테스트 코드·테스트 러너로 남기는 것이 좋다.

**실행 방식:** 사용자 또는 에이전트가 CLI를 호출한다.
skill을 추가하는 것만으로 매 수정 후 테스트가 자동 실행되지는 않는다.
공식 README는 skill 없이 CLI 도움말을 사용하는 경로도 제공한다.

**전제·상태:** 공식 README 기준 Node.js 18 이상과 브라우저 준비가 필요하다.
기본은 headless이며 브라우저를 종료할 때 기본 메모리 프로필은 사라진다.
호출 사이의 세션 상태 유지와 디스크에 프로필을 저장하는 `--persistent`는 구분한다.

**비용·데이터:** 기본 브라우저 제어 자체에 별도 LLM API가 필수는 아니다.
Claude 사용량은 별도이고, 방문한 사이트와 브라우저가 통신하며 결과가 모델에 전달될 수 있다.
제작자의 효율 주장을 이 환경에서 측정하지 않았으므로 MCP 대비 절감률을 단정하지 않는다.
판단: 새 웹 개발 구성에서는 CLI+skills 또는 Playwright MCP 중 하나를 먼저 선택한다.

## 8. agent-browser — 별도 CLI 방식이 맞을 때 조건부 대안

**유형:** Vercel Labs의 네이티브 브라우저 자동화 CLI + 선택적 skill.

페이지 스냅샷의 `@e1` 같은 요소 참조로 클릭·입력하고, 스크린샷이나 CDP 연결을 사용한다.
특정 원격 브라우저 서비스 연동이나 이 CLI의 조작 방식이 필요할 때 비교할 만하다.
Playwright CLI/MCP와 같은 범주의 대안이며 추가 필수 도구는 아니다.

**실행 방식:** CLI/skill 호출이 있어야 작업한다.
데몬이 브라우저 상태를 유지하는 것과 작업을 알아서 시작하는 것은 다르다.
Claude 설정 없이 CLI를 설치했다고 모든 웹 작업이 이 도구로 전환되지는 않는다.

**전제:** 현재 README는 네이티브 데몬에 Node.js와 Playwright가 필요하지 않다고 설명한다.
Chrome 계열 브라우저는 필요하며, 기존 설치를 발견하거나 브라우저를 준비하는 경로가 있다.
npm으로 설치하는 방법의 요구사항과 소스 빌드 요구사항을 데몬의 필수 런타임과 혼동하지 않는다.

**비용·데이터:** 로컬 브라우저 경로와 원격 브라우저 제공자 연결을 구분한다.
Browserbase·Browserless·Kernel 등 원격 옵션은 해당 서비스의 인증·과금·처리 조건이 추가된다.
선택적 AI chat 기능도 있으므로 모든 실행 모드를 동일한 비용 구조로 묶지 않는다.
로컬 실행도 웹사이트와 통신하며, 스냅샷·화면 정보는 에이전트가 읽는다.

**선택 판단:** CLI 조작 방식이나 특정 제공자 연동이 선택 근거일 때 채택한다.
Playwright 도구와 함께 기본 설치하는 조합은 피한다.
속도·토큰 절감에 대한 제작자 수치를 비교 실측 결과로 인용하지 않았다.
출처: [Vercel Labs 공식 README](https://github.com/vercel-labs/agent-browser).

## 9. 공식 Dart/Flutter MCP·플러그인 — 해당 언어 사용자에게 우선

**유형:** Dart SDK의 로컬 stdio MCP 서버와 Flutter 팀 공식 plugin.

분석기 진단·심볼 정보뿐 아니라 실행 중 Flutter 앱 오류, 위젯 트리, hot reload/restart를 다룬다.
Flutter UI를 수정하고 실행 상태를 확인하는 작업에서 기존 LSP/Serena보다 분명한 추가 역할이 있다.
지원 기능과 노출되는 도구는 SDK·설정에 따라 확인해야 한다. [Flutter 도구 구조](https://docs.flutter.dev/ai/tools)

**공식성 구분:** 현재 공식 안내는 `flutter/agent-plugins`의 `dart-flutter` plugin을 가리킨다.
같은 이름의 외부 패키지와 혼동하지 말고 제작자·marketplace를 함께 확인한다.
플러그인이 skills와 MCP 구성을 제공하는 것과 SDK MCP만 연결하는 방법을 구별한다. [공식 플러그인 저장소](https://github.com/flutter/agent-plugins)

**자동 실행 주의:** Claude Code는 plugin의 skills/MCP를 찾지만 plugin rules를 자동으로 읽지는 않는다.
공식 문서는 원하는 Flutter rules를 프로젝트 `CLAUDE.md`에 별도로 추가하도록 안내한다.
따라서 plugin 설치만으로 위젯 수정 후 reload 규칙까지 적용된다고 설명하면 안 된다. [공식 시작 문서](https://docs.flutter.dev/ai/get-started)

**전제:** 지원 Dart/Flutter SDK가 PATH에 있어야 한다.
실행 중 앱을 조사하려면 Dart Tooling Daemon 연결 등 해당 실행 환경이 필요하다.
앱 실행 모드와 `--no-dds` 같은 옵션은 연결 가능성에 영향을 줄 수 있다.

**비용·데이터:** SDK 분석·앱 제어는 로컬 환경을 사용하지만 pub.dev 조회 등은 네트워크 통신이다.
도구 결과는 Claude에 전달되고, 별도의 Developer Knowledge MCP는 클라우드 서비스다.
전체 도구를 완전 오프라인이라고 묶지 않는다.
구현 README에는 experimental/WIP 설명이 남아 있으므로 프로젝트 호환성을 확인한다. [Dart MCP 구현](https://github.com/dart-lang/ai/tree/main/pkgs/dart_mcp_server)

## 10. Docker MCP Toolkit — 여러 서버를 관리할 때 조건부

**유형:** Docker Desktop 관리 UI + 컨테이너 기반 MCP 실행·Gateway·프로필 관리.

프로젝트마다 필요한 MCP 서버 조합이 다르고, 서버별 의존성 관리가 번거로울 때 유용하다.
새 코드 검색 기능이나 기억 기능을 주는 단일 MCP 서버가 아니라 서버를 운영하는 계층이다.
한두 개 MCP만 쓴다면 추가 계층의 필요가 작다.

**전제·상태:** Docker Desktop과 Toolkit 활성화가 필요하다.
현재 문서는 Toolkit을 Beta로 표시하며, 현재 UI 문서의 대상 버전과 개별 기능의 최소 버전은 다를 수 있다.
이미 Docker를 사용하는 환경에서 검토하는 편이 자연스럽다. [공식 Toolkit 문서](https://docs.docker.com/ai/mcp-catalog-and-toolkit/toolkit/)

**자동 실행 주의:** Gateway의 Dynamic MCP는 기본 활성화라고 문서에 설명되어 있다.
에이전트가 `mcp-find`·`mcp-add`로 대화 중 서버를 검색·추가할 수 있다.
이렇게 추가한 서버는 세션 범위이며 프로필에 영구 저장되는 것은 아니다.
고정 구성만 원하는 경우 동적 도구를 비활성화하는 방식을 검토한다.

**데이터:** 컨테이너의 호스트 파일 접근은 마운트 범위와 관계가 있다.
컨테이너를 쓴다는 사실이 연결된 서버의 외부 API·OAuth 통신까지 막는다는 뜻은 아니다.
처리 경로와 권한은 실제 추가한 서버별로 확인한다.

**비용:** 로컬 자원, Claude 사용량, 외부 서비스 요금과 별도로 조직의 Docker Desktop 라이선스 조건이 있다.
출처: [Docker Desktop 라이선스](https://docs.docker.com/subscription-billing/desktop-license/).

**보류할 기능:** Dynamic MCP의 experimental code-mode는 공식 문서가 일반 사용의 신뢰성 한계를 명시한다.
현재 기본 추천 구성에는 포함하지 않는다. [Dynamic MCP 문서](https://docs.docker.com/ai/mcp-catalog-and-toolkit/dynamic-mcp/)

## 작업별로 합치면

| 사용자 상황 | 기존 구성에 더할 후보 | 먼저 생략할 것 |
|---|---|---|
| 일반 앱·백엔드 개발 | 구조 변경이 많으면 ast-grep, 자료 전달 시 Repomix | 별도 색인 MCP 중복 |
| 웹 UI 개발 | Playwright CLI+skills 또는 기존 Playwright MCP | agent-browser까지 동시 기본 설치 |
| Flutter 개발 | Flutter 팀 공식 plugin 또는 SDK MCP | 실행 도구 목적 없는 브라우저 MCP |
| 긴 테스트 로그 반복 | RTK의 명령 출력 필터부터 검토 | 처음부터 proxy·라우팅 추가 |
| 규칙 기반 보안 검사 | Semgrep Guardian 또는 기존 검사 체계 | 여러 자동 보안 hook의 무조건 중첩 |
| 회사의 여러 저장소 탐색 | 회사가 쓰는 Sourcegraph MCP | 개인 저장소용 새 Enterprise 도입 |
| MCP 서버 운영 부담 | Docker Toolkit/Gateway | 단순 구성을 위한 불필요한 관리 계층 |

범용 추가 후보 세 개를 고르면 **ast-grep, Repomix, Playwright CLI+skills**다.
각각 구조 검색, 자료 묶음, 웹 작업이라는 역할이 분명하며 필요한 작업에 한해 선택한다.
Flutter/Dart 프로젝트라면 Playwright 대안 비교보다 **공식 Dart/Flutter 도구**를 먼저 검토한다.
RTK는 긴 출력이라는 문제가 있을 때, jCodeMunch는 기존 심볼 탐색으로 부족할 때 평가한다.

## 조사에서 확인한 정정 사항

- Semgrep의 옛 독립 MCP 저장소는 보관되었지만 현재 Guardian/MCP 기능까지 폐기된 것은 아니다.
- Guardian 권장 원격 경로는 평가판 이후 유료이며, Sourcegraph MCP는 Enterprise 조건이 있다.
- jCodeMunch는 비상업·상업 사용 라이선스가 다르다.
- RTK는 순수 CLI 필터만 있는 단일 구성으로 설명하기 어렵고, 배포판·엔진·proxy를 구별해야 한다.
- agent-browser의 현재 네이티브 데몬에 Node.js·Playwright가 필수라는 안내는 맞지 않는다.
- 공식 Flutter plugin이 존재하지만 Claude Code의 plugin rules 자동 적용은 별개다.
- Repomix MCP와 Dart MCP의 실험적 설명, Docker Toolkit Beta 상태를 안정성 검증으로 바꾸어 쓰지 않았다.
- 설치 성공·실제 호환성·속도·품질·요금 절감은 이번 문서 조사로 검증하지 않았다.
